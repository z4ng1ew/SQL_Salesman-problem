# 📦 Где ИМЕННО хранятся VIEW и MATERIALIZED VIEW по уровням

## 🎨 **EXTERNAL LEVEL (Внешний уровень)**

### VIEW ✅

**Что хранится:** Интерфейс для пользователя

```sql
-- Пользователь видит VIEW как обычную таблицу:
SELECT * FROM v_females;
```

**Для пользователя VIEW выглядит как таблица!** Он не знает, что это виртуально.

```
👤 Пользователь видит:
┌──────────────────────┐
│ v_females            │
│ ├─ id                │
│ ├─ name              │
│ └─ age               │
└──────────────────────┘

Кажется обычной таблицей!
```

### MATERIALIZED VIEW ✅

**Что хранится:** Тоже интерфейс для пользователя

```sql
-- Пользователь тоже видит как таблицу:
SELECT * FROM mv_females;
```

**Внешне VIEW и MVIEW неразличимы для пользователя!**

---

## 🧩 **CONCEPTUAL LEVEL (Концептуальный уровень)**

Здесь хранятся **ОПРЕДЕЛЕНИЯ** и **МЕТАДАННЫЕ**

### VIEW ✅

**Что хранится:** SQL-текст определения VIEW

```sql
-- Определение VIEW хранится в системной таблице:
CREATE VIEW v_females AS
SELECT id, name, age, address
FROM person
WHERE gender = 'female';
```

**Где конкретно?** В системных таблицах PostgreSQL:

```sql
-- Смотрим определение VIEW:
SELECT definition 
FROM pg_views 
WHERE viewname = 'v_females';

-- Результат:
-- "SELECT id, name, age, address FROM person WHERE gender = 'female';"
```

**Структура в БД:**

```
pg_class (системная таблица)
├─ relname = 'v_females'
├─ relkind = 'v'  ← маркер "это VIEW"
└─ oid = 16385

pg_rewrite (правила перезаписи)
└─ ev_action = "SELECT id, name FROM person WHERE..."
```

**Аналогия:**

```javascript
// Концептуально VIEW хранится как:
const viewDefinitions = {
    'v_females': {
        type: 'VIEW',
        sql: 'SELECT id, name FROM person WHERE gender = "female"'
    }
};
```

---

### MATERIALIZED VIEW ✅

**Что хранится:** 
1. SQL-текст определения (как у VIEW)
2. **ПЛЮС метаданные о физической таблице!**

```sql
CREATE MATERIALIZED VIEW mv_females AS
SELECT id, name, age, address
FROM person
WHERE gender = 'female';
```

**Где конкретно?** В системных таблицах:

```sql
-- Смотрим определение MVIEW:
SELECT definition 
FROM pg_matviews 
WHERE matviewname = 'mv_females';

-- Результат тот же SQL
```

**Структура в БД:**

```
pg_class (системная таблица)
├─ relname = 'mv_females'
├─ relkind = 'm'  ← маркер "это MATERIALIZED VIEW"
├─ relfilenode = 16390  ← ССЫЛКА НА ФИЗИЧЕСКИЙ ФАЙЛ!
└─ relpages = 10  ← сколько страниц занимает на диске
```

**Ключевое отличие от VIEW:**

```
VIEW:
- Определение: ✅ есть
- Ссылка на файл: ❌ нет

MATERIALIZED VIEW:
- Определение: ✅ есть
- Ссылка на файл: ✅ ЕСТЬ! (relfilenode)
```

## 💾 **INTERNAL LEVEL (Внутренний уровень)**

Здесь хранятся **ФИЗИЧЕСКИЕ ДАННЫЕ** на диске

### VIEW ❌

**Что хранится:** НИЧЕГО!

```
🚫 НЕТ файла с данными
🚫 НЕТ индексов
🚫 НЕТ физического хранения
```

**Почему?** VIEW - это просто **SQL-текст**, который выполняется каждый раз.

**Аналогия:**

```javascript
// VIEW - это функция без кэша:
function v_females() {
    return db.query("SELECT * FROM person WHERE gender='female'");
}

// Данные НЕ сохраняются, каждый раз новый запрос!
```

---

### MATERIALIZED VIEW ✅

**Что хранится:** РЕАЛЬНЫЙ ФАЙЛ С ДАННЫМИ!

```
📁 Физический файл: /var/lib/postgresql/data/base/16384/16390
📊 Данные: все строки результата SELECT
📇 Индексы: можно создать дополнительно
```

**Пример:**

```sql
-- Создали MVIEW:
CREATE MATERIALIZED VIEW mv_females AS
SELECT id, name, age FROM person WHERE gender = 'female';

-- PostgreSQL ФИЗИЧЕСКИ сохранил:
┌────┬────────┬─────┐
│ id │ name   │ age │
├────┼────────┼─────┤
│ 2  │ Anna   │ 16  │
│ 3  │ Kate   │ 33  │
│ 4  │ Denis  │ 13  │  ← ошибка в данных, но сохранилась!
└────┴────────┴─────┘

В файле на диске: /var/lib/.../16390
```

**Можно создать индексы:**

```sql
-- Создаём индекс на MVIEW (на VIEW нельзя!):
CREATE INDEX idx_mv_females_age ON mv_females(age);

-- Теперь есть ДВА физических файла:
-- 1. Файл с данными: 16390
-- 2. Файл с индексом: 16391
```

**Аналогия:**

```javascript
// MATERIALIZED VIEW - это переменная с кэшем:
let mv_females = db.query("SELECT * FROM person WHERE gender='female'");

// Данные СОХРАНЕНЫ в памяти/на диске
// Можно быстро читать без повторного запроса
```

---

## 📊 Полная таблица сравнения

| Уровень | VIEW | MATERIALIZED VIEW |
|---------|------|-------------------|
| **🎨 External** | ✅ Видна пользователю как таблица | ✅ Видна пользователю как таблица |
| **🧩 Conceptual** | ✅ SQL-определение в `pg_views` | ✅ SQL-определение в `pg_matviews` + метаданные физ. таблицы |
| **💾 Internal** | ❌ НЕТ данных на диске | ✅ ЕСТЬ физический файл с данными |

## 🔍 Проверка на практике

### Найти VIEW в системных таблицах:

```sql
-- Все VIEW в базе:
SELECT schemaname, viewname, definition
FROM pg_views
WHERE schemaname = 'public';

-- Результат:
┌────────────┬────────────┬─────────────────────────────┐
│ schemaname │ viewname   │ definition                  │
├────────────┼────────────┼─────────────────────────────┤
│ public     │ v_females  │ SELECT id, name FROM...     │
└────────────┴────────────┴─────────────────────────────┘
```

---

### Найти MATERIALIZED VIEW в системных таблицах:

```sql
-- Все MVIEW в базе:
SELECT schemaname, matviewname, definition
FROM pg_matviews
WHERE schemaname = 'public';

-- Результат:
┌────────────┬──────────────┬─────────────────────────────┐
│ schemaname │ matviewname  │ definition                  │
├────────────┼──────────────┼─────────────────────────────┤
│ public     │ mv_females   │ SELECT id, name FROM...     │
└────────────┴──────────────┴─────────────────────────────┘
```

---

### Найти физические файлы MVIEW:

```sql
-- Получить номер файла MVIEW:
SELECT relname, relfilenode, relpages, reltuples
FROM pg_class
WHERE relname = 'mv_females';

-- Результат:
┌─────────────┬──────────────┬──────────┬───────────┐
│ relname     │ relfilenode  │ relpages │ reltuples │
├─────────────┼──────────────┼──────────┼───────────┤
│ mv_females  │ 16390        │ 5        │ 150       │
└─────────────┴──────────────┴──────────┴───────────┘

-- Физический файл: /var/lib/postgresql/data/base/[db_oid]/16390
-- Занимает: 5 страниц по 8KB = 40KB
-- Строк: 150
```

---

### Проверить VIEW (файла НЕТ):

```sql
SELECT relname, relfilenode, relpages, reltuples
FROM pg_class
WHERE relname = 'v_females';

-- Результат:
┌─────────────┬──────────────┬──────────┬───────────┐
│ relname     │ relfilenode  │ relpages │ reltuples │
├─────────────┼──────────────┼──────────┼───────────┤
│ v_females   │ 0            │ 0        │ 0         │
└─────────────┴──────────────┴──────────┴───────────┘

-- relfilenode = 0  ← НЕТ физического файла!
-- relpages = 0     ← не занимает места на диске
```

## 💡 Простая аналогия

### VIEW = Ярлык на рабочем столе

```
External:      Иконка ярлыка (двойной клик)
Conceptual:    Путь к программе (C:\Program Files\...)
Internal:      НИЧЕГО! Ярлык не занимает места
```

Когда кликаешь — каждый раз запускается программа заново.

---

### MATERIALIZED VIEW = Скриншот программы

```
External:      Картинка на рабочем столе
Conceptual:    Метаданные (размер, дата создания)
Internal:      ФАЙЛ screenshot.png на диске (занимает место!)
```

Когда открываешь — сразу видишь картинку (быстро), но она может устареть.

---

## 🧠 Итоговое резюме

| Уровень | Что это | VIEW | MATERIALIZED VIEW |
|---------|---------|------|-------------------|
| **External** | Что видит пользователь | Таблица | Таблица |
| **Conceptual** | Логическая схема | SQL-текст | SQL-текст + ссылка на файл |
| **Internal** | Физическое хранение | ❌ Пусто | ✅ Реальный файл |

### Запомни:

```
VIEW = только определение (рецепт)
MATERIALIZED VIEW = определение + готовое блюдо

Уровни:
🎨 External = интерфейс (оба одинаковы)
🧩 Conceptual = SQL-код (у MVIEW + метаданные файла)
💾 Internal = VIEW ничего, MVIEW файл с данными!
```
