# 🔢 BIGINT - тип данных для больших целых чисел

## 📝 Что такое BIGINT?

**BIGINT** = **Big Integer** = **Большое целое число**

**Расшифровка:**
- **BIG** (английский) = большой, огромный
- **INT** = сокращение от INTEGER (целое число)
- **BIGINT** = "большой integer", тип для очень больших целых чисел

---

## 🎯 Простое определение

**BIGINT** - это тип данных в SQL для хранения **больших целых чисел** (без дробной части).

```
BIGINT может хранить числа от -9,223,372,036,854,775,808
                       до  9,223,372,036,854,775,807
                       
Это примерно ±9 квинтиллионов!
```

---

## 📊 Технические характеристики

### В PostgreSQL:

| Характеристика | Значение |
|----------------|----------|
| **Размер** | 8 байт (64 бита) |
| **Минимум** | -9,223,372,036,854,775,808 |
| **Максимум** | 9,223,372,036,854,775,807 |
| **Знаковый** | Да (signed) |
| **Дробная часть** | Нет (только целые) |

---

## 🔄 Аналог в C (ты знаешь C!)

### В языке C:

```c
// BIGINT в PostgreSQL = long long в C (на 64-битных системах)

long long x = 9223372036854775807LL;  // максимум BIGINT
long long y = -9223372036854775808LL; // минимум BIGINT

// Также может быть:
int64_t z = 123456789012345LL;  // явный 64-битный тип

// Размер:
sizeof(long long) = 8 байт = 64 бита
```

**SQL BIGINT ≈ C `long long` или `int64_t`**

---

## 🔄 Аналог в JavaScript (ты знаешь JS!)

### В JavaScript:

```javascript
// До ES2020: проблемы с большими числами
let x = 9007199254740991;  // Number.MAX_SAFE_INTEGER
let y = 9007199254740992;  // уже неточно!
x + 1 === y + 1;  // true (!) - потеря точности

// ES2020: BigInt (аналог BIGINT)
let bigNum = 9223372036854775807n;  // буква 'n' в конце
let bigNum2 = BigInt("9223372036854775807");

// Операции с BigInt:
let result = 100n + 200n;  // 300n
let huge = 999999999999999999999999n;  // работает!

// Но нельзя смешивать:
100n + 200;  // ERROR: Cannot mix BigInt and other types
```

**SQL BIGINT ≈ JS `BigInt` (с ES2020)**

## 📏 Сравнение типов целых чисел в PostgreSQL

### Основные типы:

| Тип | Размер | Минимум | Максимум | Когда использовать |
|-----|--------|---------|----------|-------------------|
| **SMALLINT** | 2 байта | -32,768 | 32,767 | Маленькие числа (возраст, счётчики) |
| **INTEGER (INT)** | 4 байта | -2,147,483,648 | 2,147,483,647 | Обычные числа (ID до 2 млрд) |
| **BIGINT** | 8 байт | -9×10¹⁸ | 9×10¹⁸ | Очень большие числа |

---

### Визуализация диапазонов:

```
SMALLINT:    [-32K .............. +32K]
                    ↑ маленький диапазон

INTEGER:     [-2 млрд ........... +2 млрд]
                    ↑ обычный диапазон

BIGINT:      [-9 квинтиллионов ... +9 квинтиллионов]
                    ↑ ОГРОМНЫЙ диапазон!
```

---

## 💾 Размер в памяти

### Сравнение размеров:

```
SMALLINT:  ██ (2 байта)
INTEGER:   ████ (4 байта)
BIGINT:    ████████ (8 байт)

Чем больше тип → больше занимает места
Чем больше тип → больший диапазон значений
```

---

### Пример расчёта места:

```sql
-- Таблица с 1 миллионом строк:

CREATE TABLE example1 (
    id INTEGER  -- 4 байта × 1,000,000 = 4 МБ
);

CREATE TABLE example2 (
    id BIGINT   -- 8 байт × 1,000,000 = 8 МБ
);

-- Разница: 4 МБ на миллион строк
-- На 1 миллиарде строк: 4 ГБ разницы!
```

**Вывод:** Используй BIGINT только когда действительно нужен большой диапазон.

## 🎯 Когда использовать BIGINT?

### ✅ Используй BIGINT когда:

**1. ID в больших таблицах:**
```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY  -- миллиарды пользователей
);
```

**2. Финансовые суммы в копейках:**
```sql
CREATE TABLE transactions (
    amount_cents BIGINT  -- 999999999999.99₽ в копейках
);
-- 1 рубль = 100 копеек
-- Храним в копейках для точности
```

**3. Временные метки (timestamps):**
```sql
CREATE TABLE events (
    unix_timestamp BIGINT  -- секунды с 1970 года
);
-- 1609459200 = 2021-01-01 00:00:00
```

**4. Большие счётчики:**
```sql
CREATE TABLE analytics (
    page_views BIGINT,  -- миллиарды просмотров
    clicks BIGINT
);
```

**5. Уникальные идентификаторы (UUID как число):**
```sql
CREATE TABLE items (
    snowflake_id BIGINT  -- Twitter Snowflake ID
);
```

---

### ❌ НЕ используй BIGINT когда:

**1. Маленькие диапазоны:**
```sql
-- Плохо:
CREATE TABLE person (
    age BIGINT  -- возраст никогда не превысит 200
);

-- Хорошо:
CREATE TABLE person (
    age SMALLINT  -- достаточно для возраста
);
```

**2. Обычные ID:**
```sql
-- Плохо (для маленькой БД):
CREATE TABLE products (
    id BIGINT  -- всего 1000 товаров
);

-- Хорошо:
CREATE TABLE products (
    id INTEGER  -- достаточно до 2 млрд
);
```

**3. Флаги и статусы:**
```sql
-- Плохо:
CREATE TABLE orders (
    status BIGINT  -- только 3 статуса: 0, 1, 2
);

-- Хорошо:
CREATE TABLE orders (
    status SMALLINT  -- или даже BOOLEAN/ENUM
);
```

## 📐 Примеры из реальной жизни

### Пример 1: Facebook (миллиарды пользователей)

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,  -- нужен BIGINT!
    name VARCHAR(100)
);

-- Почему BIGINT?
-- Пользователей: 3,000,000,000 (3 миллиарда)
-- INTEGER макс: 2,147,483,647 (2.1 миллиарда)
-- 3 млрд > 2.1 млрд → INTEGER НЕ хватит!
```

---

### Пример 2: YouTube (миллиарды просмотров)

```sql
CREATE TABLE videos (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200),
    view_count BIGINT  -- "Gangnam Style" > 4 млрд просмотров
);

-- INTEGER макс: 2.1 млрд
-- View count: 4.6 млрд
-- Нужен BIGINT!
```

---

### Пример 3: Банковская система (копейки)

```sql
CREATE TABLE accounts (
    id INTEGER,
    balance_cents BIGINT  -- баланс в копейках
);

-- Зачем копейки?
-- Избежать проблем с FLOAT/DECIMAL

-- Пример:
-- 1,234,567.89₽ = 123,456,789 копеек (BIGINT)

-- Почему BIGINT?
-- Миллионер: 1,000,000.00₽ = 100,000,000 копеек
-- Миллиардер: 1,000,000,000.00₽ = 100,000,000,000 копеек
-- INTEGER макс: 2,147,483,647 копеек = ~21 млн рублей
-- Для миллиардеров нужен BIGINT!
```

---

### Пример 4: Unix Timestamp

```sql
CREATE TABLE logs (
    timestamp BIGINT,  -- секунды с 1970-01-01
    message TEXT
);

-- Unix timestamp:
-- 1970-01-01 = 0
-- 2024-01-01 = 1704067200
-- 2038-01-19 = 2147483647 (макс INTEGER - проблема Y2K38!)
-- 2100-01-01 = 4102444800 (нужен BIGINT!)

-- Проблема 2038 года (Y2K38):
-- INTEGER переполнится 19 января 2038 года!
-- Решение: использовать BIGINT для timestamp
```

## 🔢 Арифметика с BIGINT

### В SQL:

```sql
-- Сложение:
SELECT 9223372036854775800::BIGINT + 5;
-- Результат: 9223372036854775805

-- Вычитание:
SELECT 1000000000000::BIGINT - 999999999999::BIGINT;
-- Результат: 1

-- Умножение:
SELECT 1000000::BIGINT * 1000000::BIGINT;
-- Результат: 1000000000000

-- Деление (целочисленное):
SELECT 100::BIGINT / 3::BIGINT;
-- Результат: 33 (дробная часть отбрасывается!)

-- Остаток от деления:
SELECT 100::BIGINT % 3::BIGINT;
-- Результат: 1
```

---

### Переполнение (overflow):

```sql
-- Попытка превысить максимум:
SELECT 9223372036854775807::BIGINT + 1;
-- ERROR: bigint out of range

-- Решение: использовать NUMERIC для ещё больших чисел:
SELECT 9223372036854775807::NUMERIC + 1;
-- Результат: 9223372036854775808 (работает!)
```

---

## 🔄 Приведение типов

### BIGINT ↔ другие типы:

```sql
-- INTEGER → BIGINT (автоматически):
SELECT 123::INTEGER::BIGINT;
-- Результат: 123 (тип BIGINT)

-- BIGINT → INTEGER (опасно!):
SELECT 9999999999::BIGINT::INTEGER;
-- ERROR: integer out of range (не влезает!)

-- Безопасное приведение:
SELECT 1000::BIGINT::INTEGER;
-- Результат: 1000 (влезло)

-- VARCHAR → BIGINT:
SELECT '12345678901234'::BIGINT;
-- Результат: 12345678901234

-- BIGINT → VARCHAR:
SELECT 9223372036854775807::BIGINT::VARCHAR;
-- Результат: '9223372036854775807'

-- NUMERIC → BIGINT (с потерей дробной части):
SELECT 123.456::NUMERIC::BIGINT;
-- Результат: 123 (отбросили .456)
```

## 📊 Использование в SQL Bootcamp

### В наших таблицах:

```sql
-- Таблица person:
CREATE TABLE person (
    id BIGINT PRIMARY KEY,  -- ← BIGINT для ID
    name VARCHAR(100),
    age INTEGER,
    gender VARCHAR(10),
    address VARCHAR(200)
);

-- Таблица person_visits:
CREATE TABLE person_visits (
    id BIGINT PRIMARY KEY,        -- ← BIGINT
    person_id BIGINT,              -- ← BIGINT (foreign key)
    pizzeria_id BIGINT,            -- ← BIGINT (foreign key)
    visit_date DATE
);

-- Почему BIGINT для ID?
-- 1. Стандарт PostgreSQL для auto-increment ID
-- 2. Запас на будущее (если таблица вырастет)
-- 3. Совместимость с другими системами
```

## ⚠️ Частые ошибки

### Ошибка 1: Переполнение при вычислениях

```sql
-- Плохо:
SELECT 1000000 * 1000000;  -- тип INTEGER!
-- Результат: ERROR (переполнение)

-- Хорошо:
SELECT 1000000::BIGINT * 1000000::BIGINT;
-- Результат: 1000000000000 (работает!)
```

---

### Ошибка 2: Смешивание типов

```sql
-- Проблема:
CREATE TABLE test (
    id INTEGER
);

INSERT INTO test VALUES (1);

SELECT * FROM test WHERE id = 1::BIGINT;
-- Работает, но неэффективно (приведение типов)

-- Лучше:
SELECT * FROM test WHERE id = 1;
-- Типы совпадают → быстрее
```

---

### Ошибка 3: Ненужное использование BIGINT

```sql
-- Плохо (расход памяти):
CREATE TABLE products (
    id BIGINT,           -- 8 байт
    quantity BIGINT,     -- 8 байт
    status BIGINT        -- 8 байт
);
-- Итого: 24 байта на строку

-- Хорошо (оптимизация):
CREATE TABLE products (
    id INTEGER,          -- 4 байта (до 2 млрд товаров)
    quantity INTEGER,    -- 4 байта (до 2 млрд штук)
    status SMALLINT      -- 2 байта (статусов мало)
);
-- Итого: 10 байт на строку
-- Экономия: 14 байт × 1,000,000 строк = 14 МБ
```

## 🧠 Резюме

| Аспект | Описание |
|--------|----------|
| **Что такое** | Тип данных для больших целых чисел |

| **Диапазон** | -9×10¹⁸ до 9×10¹⁸ |

## 🎯 Простое объяснение

```
BIGINT = тип для ОЧЕНЬ БОЛЬШИХ целых чисел

Диапазон:
SMALLINT:  -32 тысячи ... +32 тысячи
INTEGER:   -2 миллиарда ... +2 миллиарда
BIGINT:    -9 квинтиллионов ... +9 квинтиллионов
           ↑ это ОГРОМНОЕ число!

Примеры использования:
✅ ID пользователей Facebook (миллиарды)
✅ Просмотры видео на YouTube (миллиарды)
✅ Unix timestamp (до 2100 года и дальше)
✅ Деньги в копейках (для точности)
✅ Большие счётчики

Аналоги:
C:  long long (8 байт)
JS: BigInt (с буквой 'n')
SQL: BIGINT
```

## 📌 Запомни:

```
BIGINT = BIG + INTEGER
         ↑     ↑
      большой  целое число

Размер: 8 байт (64 бита)
Диапазон: ±9,223,372,036,854,775,807

Когда использовать:
"Может ли это число превысить 2 миллиарда?"
→ ДА: используй BIGINT
→ НЕТ: используй INTEGER

"Может ли это число превысить 32 тысячи?"
→ НЕТ: используй SMALLINT
```

**Правило:** Выбирай минимальный тип, который ТОЧНО вместит твои данные! 🎯
