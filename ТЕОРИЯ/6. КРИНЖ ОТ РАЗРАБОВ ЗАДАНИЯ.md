# 🔗 Что такое ЗАВИСИМОСТИ? (на пальцах!)

## 🎯 Простое определение

**ЗАВИСИМОСТЬ** = когда один кусок кода **использует** другой кусок кода

```
Код A зависит от Кода B
       ↓
Если изменить Код B → Код A может сломаться
```

---

## 🍕 Аналогия с пиццерией

### Плохой вариант (прямая зависимость):

```
Курьер → идёт на склад → берёт конкретную коробку #5
```

**Проблема:**
- Переставили коробки? ❌ Курьер не найдёт
- Заменили коробку? ❌ Курьер растеряется
- Добавили новый склад? ❌ Курьер не знает

**Курьер ЗАВИСИТ от расположения коробок!**

---

### Хороший вариант (через абстракцию):

```
Курьер → говорит повару "дай пиццу" → повар сам идёт на склад
```

**Преимущество:**
- Переставили коробки? ✅ Повар знает
- Заменили коробку? ✅ Повар разберётся
- Добавили склад? ✅ Повар найдёт

**Курьер НЕ зависит от склада!** Он зависит только от повара (абстракция).

---

## 💻 Пример на JavaScript (ты знаешь JS!)

### ❌ ПЛОХО - Прямая зависимость:

```javascript
// Приложение НАПРЯМУЮ работает с БД
function getUsers() {
    // Код зависит от структуры таблицы person
    const query = "SELECT id, name, age, gender FROM person";
    return database.execute(query);
}

// Используем в 50 местах приложения:
const users1 = getUsers();  // место 1
const users2 = getUsers();  // место 2
// ... 48 раз ещё
```

**Что будет, если переименовать колонку?**

```sql
-- БД изменилась:
ALTER TABLE person RENAME COLUMN name TO full_name;
```

💥 **БАБАХ!** Все 50 мест в приложении СЛОМАЛИСЬ!

Теперь нужно найти и исправить:
```javascript
// В 50 местах менять:
"SELECT id, name, age..."  →  "SELECT id, full_name, age..."
```

**Приложение СИЛЬНО ЗАВИСИТ от структуры БД!**

---

### ✅ ХОРОШО - Через абстракцию (VIEW):

```sql
-- Создали VIEW (абстракцию):
CREATE VIEW v_users AS
SELECT id, name, age, gender FROM person;
```

```javascript
// Приложение работает с VIEW:
function getUsers() {
    const query = "SELECT * FROM v_users";  // через VIEW!
    return database.execute(query);
}

// 50 мест в приложении:
const users1 = getUsers();  // место 1
const users2 = getUsers();  // место 2
// ... 48 раз ещё
```

**Что будет, если переименовать колонку?**

```sql
-- БД изменилась:
ALTER TABLE person RENAME COLUMN name TO full_name;

-- Исправляем ТОЛЬКО VIEW (1 место!):
CREATE OR REPLACE VIEW v_users AS
SELECT id, full_name AS name, age, gender FROM person;
--            ↑ новое имя    ↑ показываем как "name"
```

✅ **ВСЁ РАБОТАЕТ!** Все 50 мест в приложении не изменились!

**Приложение СЛАБО ЗАВИСИТ от БД** (зависит только от VIEW).

## 🔧 Пример на языке C (ты знаешь C!)

### ❌ ПЛОХО - Прямая зависимость:

```c
// main.c - зависит от структуры Person
#include <stdio.h>

struct Person {
    int id;
    char name[50];
    int age;
};

void printPerson(struct Person p) {
    printf("%s, %d years\n", p.name, p.age);
}

int main() {
    struct Person p = {1, "Anna", 25};
    printPerson(p);
    return 0;
}
```

**Проблема:** Если структура изменится...

```c
// Изменили структуру:
struct Person {
    int id;
    char first_name[30];  // было name
    char last_name[30];   // новое поле!
    int age;
};
```

💥 **Весь код сломался!** Нужно менять везде:
```c
printf("%s, %d years\n", p.name, p.age);  // ❌ не компилируется!
// Нужно менять на:
printf("%s %s, %d years\n", p.first_name, p.last_name, p.age);
```

---

### ✅ ХОРОШО - Через абстракцию (функцию-интерфейс):

```c
// person.h - интерфейс (абстракция)
typedef struct Person Person;  // скрываем детали

char* person_get_name(Person* p);
int person_get_age(Person* p);

// main.c - зависит только от интерфейса
#include "person.h"

void printPerson(Person* p) {
    printf("%s, %d years\n", 
           person_get_name(p),   // через функцию!
           person_get_age(p));
}
```

**Если структура изменится:**

```c
// person.c - реализация
struct Person {
    int id;
    char first_name[30];
    char last_name[30];
    int age;
};

char* person_get_name(Person* p) {
    // ТОЛЬКО здесь меняем код:
    static char full_name[60];
    sprintf(full_name, "%s %s", p->first_name, p->last_name);
    return full_name;
}
```

✅ **main.c НЕ ИЗМЕНИЛСЯ!** Код работает как прежде.

## 🕸️ Визуализация зависимостей

### Без абстракции (всё зависит от всего):

```
    МобильноеПриложение ────┐
                            │
    Сайт ───────────────────┼─────> Таблица person
                            │
    API ────────────────────┘

Изменили таблицу? 
→ Сломались 3 места! 💥💥💥
```

---

### С абстракцией (все зависят от VIEW):

```
    МобильноеПриложение ────┐
                            │
    Сайт ───────────────────┼─────> VIEW v_users ───> Таблица person
                            │
    API ────────────────────┘

Изменили таблицу?
→ Исправили VIEW
→ Приложения работают! ✅✅✅
```

## 📊 Типы зависимостей

### 1. **Сильная зависимость** (плохо):

```javascript
// Код знает ВСЁ о структуре данных:
const name = database.person.fields.name.value;
const age = database.person.fields.age.value;

// Изменилась структура → код сломался
```

**Аналогия:** Ты заказываешь пиццу и говоришь: "Возьми муку из шкафа №3, полка 2, слева. Добавь томаты из холодильника, отдел овощей, нижняя полка..."

---

### 2. **Слабая зависимость** (хорошо):

```javascript
// Код просит через интерфейс:
const user = getUserData();  // не знаем, откуда данные
const name = user.name;
const age = user.age;

// Внутри может что угодно измениться
```

**Аналогия:** Ты говоришь: "Пиццу Маргарита, пожалуйста". Повар сам знает, где взять ингредиенты.

## 🎯 Зачем минимизировать зависимости?

### Проблемы сильных зависимостей:

1. **Хрупкий код** 🏚️
   - Изменение в одном месте ломает 100 других мест
   
2. **Сложно тестировать** 🧪
   - Нельзя протестировать код без всей БД
   
3. **Невозможно заменить** 🔒
   - Хочешь заменить PostgreSQL на MySQL? Переписывай всё!

---

### Преимущества слабых зависимостей:

1. **Гибкий код** 💪
   - Изменения в одном месте, работает везде
   
2. **Легко тестировать** ✅
   - Можешь подставить "фейковую" VIEW для тестов
   
3. **Легко заменить** 🔄
   - Поменял реализацию VIEW — всё работает

## 🏗️ Связь с "Чистой архитектурой"

Помнишь картинку из первого вопроса?

```
         Внешний слой
              ↓
         Средний слой
              ↓
         Внутренний слой
```

**Правило:** Стрелки зависимостей идут **ТОЛЬКО ВНУТРЬ**

```
UI ─────> USE CASES ─────> ENTITIES

✅ UI зависит от USE CASES
✅ USE CASES зависят от ENTITIES
❌ ENTITIES НЕ зависят ни от чего!
```

**В базах данных:**

```
Приложение ─────> VIEW ─────> Таблицы

✅ Приложение зависит от VIEW
✅ VIEW зависит от таблиц
❌ Таблицы НЕ зависят от VIEW!
```

## 💡 Почему "(иногда это работает :-)"?

Автор пошутил, потому что на практике:

### Идеал:
```
Изменили БД → поменяли VIEW → всё работает! ✅
```

### Реальность:
```
Изменили БД → поменяли VIEW → 
→ нашли 5 мест, где обошли VIEW 😅
→ исправили их тоже
→ всё работает! ✅ (с доработкой)
```

**Проблема:** Программисты иногда ленятся и пишут:
```sql
-- Вместо:
SELECT * FROM v_users;

-- Пишут напрямую:
SELECT * FROM person;  -- обошли VIEW!
```

И тогда абстракция не спасает 🤷

## 🧠 Итоговое резюме

| Понятие | Простыми словами | Пример |
|---------|------------------|--------|
| **Зависимость** | Код A использует код B | `getUsers()` использует таблицу `person` |
| **Проблема** | Изменение B ломает A | Переименовали колонку → сломалось 50 мест |
| **Абстракция** | Прослойка между A и B | VIEW между приложением и таблицей |
| **Минимальное влияние** | Изменение B → правим только VIEW | Переименовали колонку → правим 1 VIEW вместо 50 мест |

---

## 📌 Запомни:

> **ЗАВИСИМОСТЬ** = когда один код знает слишком много про другой код
>
> **АБСТРАКЦИЯ** (VIEW) = "незнайка" посередине, который прячет детали
>
> **Цель:** Изменения в БД → правим VIEW → приложение не трогаем!

### На пальцах:

```
❌ БЕЗ VIEW:
Приложение──────────>Таблица
   (знает структуру)
   
✅ С VIEW:
Приложение──>VIEW──>Таблица
  (не знает     (знает)
   структуру)
```

**VIEW = щит, который защищает приложение от изменений в БД!** 🛡️
